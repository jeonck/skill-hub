# 데이터 플랫폼 아키텍처 스타일 카탈로그

각 항목은 **정의 / 구성요소 / 적합 / 한계** 네 칸으로 고정한다. 새 스타일을 추가할
때도 같은 형식을 지킨다.

---

## 1. Lakehouse (레이크하우스)

**정의**: 객체 스토리지 위에 열린 테이블 포맷을 얹어 ACID 트랜잭션·스키마 진화·
타임 트래블을 얻고, 하나의 저장 복사본을 BI와 ML이 함께 쓰는 아키텍처.

**구성요소**: 객체 스토리지(S3/GCS/ADLS) + 테이블 포맷(Iceberg / Delta Lake / Hudi)
+ 카탈로그(Unity Catalog, Polaris, Nessie, Glue) + 분리된 쿼리 엔진(Spark, Trino,
DuckDB, Snowflake, Databricks SQL).

**적합**: BI와 ML이 같은 데이터를 봐야 할 때. 스토리지와 컴퓨트를 따로 늘리고 싶을 때.
벤더 종속을 줄이려 할 때 — 포맷이 열려 있어 엔진 교체가 데이터 이관을 요구하지 않는다.

**한계**: 소규모 테이블 다량 갱신에서는 컴팩션·파일 정리 운영 부담이 생긴다. 카탈로그를
정하지 않으면 엔진마다 테이블이 보이지 않는 사고가 난다.

---

## 2. Medallion (Bronze / Silver / Gold)

**정의**: 아키텍처가 아니라 레이크하우스 **내부의 계층 규약**. 원본(Bronze) →
정제·표준화(Silver) → 업무 집계(Gold)로 테이블을 나눈다.

**구성요소**: 계층별 스키마 규칙, 계층 간 변환 잡, 계층별 보존 정책.

**적합**: 레이크하우스를 채택한 뒤 테이블이 늘어나 소유와 신뢰 수준이 흐려질 때.

**한계**: Lakehouse·Mesh와 **대안 관계가 아니다**. 비교표에 나란히 올리면 잘못된 문서다.
계층을 3개로 강제하면 단순 파이프라인이 불필요하게 3홉이 된다.

---

## 3. Modern Data Stack (ELT)

**정의**: 관리형 커넥터로 원본을 먼저 적재하고(Load), 변환은 웨어하우스 안에서 SQL로
수행하는(Transform) 구성. ETL의 순서를 뒤집은 것이 핵심.

**구성요소**: 수집(Fivetran, Airbyte) → 클라우드 DW(Snowflake, BigQuery, Redshift)
→ 변환(dbt) → BI(Looker, Tableau) + 오케스트레이션(Airflow, Dagster).

**적합**: 팀이 작고 SQL 역량이 주력일 때. SaaS 원본이 많고 커넥터로 대부분 해결될 때.
가장 빨리 가치를 내는 구성이다.

**한계**: 비정형·대용량 ML 피처에는 DW 비용이 급격히 는다. 커넥터가 없는 원본에서
막힌다. 컴퓨트 비용이 쿼리량에 직결돼 통제가 필요하다.

---

## 4. Data Mesh (데이터 메시)

**정의**: 기술 스택이 아니라 **조직 설계**. 네 원칙 — 도메인 소유, 데이터를 제품으로,
셀프서브 플랫폼, 연합 컴퓨팅 거버넌스.

**구성요소**: 도메인별 데이터 제품(SLA·스키마 계약·문서 포함), 도메인이 스스로 쓰는
셀프서브 플랫폼, 전역 표준을 정하되 실행은 도메인이 하는 연합 거버넌스 위원회.

**적합**: 도메인 팀이 여럿이고 중앙 데이터팀이 병목일 때. 각 도메인이 자기 데이터를
운영할 인력을 실제로 가진 경우.

**한계**: 중앙팀 하나뿐인 조직에서는 성립하지 않는다 — 소유할 도메인이 없다. 플랫폼
투자 없이 원칙만 도입하면 사일로가 이름만 바뀐다. 도입 비용의 대부분이 조직 비용이다.

---

## 5. Data Fabric (데이터 패브릭)

**정의**: 분산된 원본 위에 **메타데이터 주도 통합 계층**을 얹어, 데이터를 옮기지 않고
탐색·접근·거버넌스를 통일하는 기술 아키텍처.

**구성요소**: 액티브 메타데이터, 데이터 카탈로그, 지식 그래프, 자동 계보(lineage),
가상화·연합 쿼리 엔진.

**적합**: 원본이 여러 시스템·클라우드에 흩어져 있고 물리적 통합이 불가하거나 너무 비쌀 때.
규제로 데이터 이동이 제약될 때.

**한계**: Data Mesh와 **대안 관계가 아니다** — 패브릭은 기술, 메시는 조직이라 병행이
가능하다. 메타데이터 품질이 낮으면 계층 전체가 무력해진다.

---

## 6. Lambda 아키텍처

**정의**: 배치 계층과 스피드(스트림) 계층을 함께 두고, 서빙 계층에서 둘의 결과를
합쳐 조회하는 구성.

**구성요소**: 배치 계층(전량 재계산) + 스피드 계층(최근 증분) + 서빙 계층(병합 뷰).

**적합**: 이미 검증된 배치 자산이 크고, 그 위에 실시간 뷰만 얹어야 할 때.

**한계**: **같은 로직을 두 번 구현**해 두 경로가 시간이 지나며 어긋난다. 기본값으로
제시할 스타일이 아니다 — 이중 경로를 감수할 이유를 문서에 명시하지 못하면 Kappa 계열을
먼저 검토한다.

---

## 7. Kappa 아키텍처

**정의**: 배치 계층을 없애고 **스트림 경로 하나**만 두며, 재처리는 로그를 처음부터
리플레이해 수행하는 구성.

**구성요소**: 내구성 있는 로그(Kafka, Pulsar) + 스트림 처리(Flink, Spark Structured
Streaming) + 서빙 저장소. 재처리는 오프셋 되감기.

**적합**: 지연 요구가 초 단위이고, 로직을 한 벌만 유지하고 싶을 때.

**한계**: 리플레이가 가능하려면 로그 보존 기간이 재처리 범위를 덮어야 하고, 그 보존
비용이 든다. 대규모 과거 재처리는 배치보다 느릴 수 있다.

---

## 8. Streaming Lakehouse (CDC 기반)

**정의**: 원본 DB의 변경분(CDC)을 로그로 흘려 레이크하우스 테이블에 준실시간으로
반영해, 스트림과 배치 저장소를 분리하지 않는 구성.

**구성요소**: CDC 캡처(Debezium) → 로그(Kafka) → 스트리밍 인제스트(Flink) →
테이블 포맷(Iceberg/Delta, upsert·MoR 지원) → 조회 엔진.

**적합**: 분 단위 신선도가 필요하면서 별도 실시간 저장소를 두고 싶지 않을 때.
Lakehouse를 이미 쓰고 있고 신선도만 올리려 할 때.

**한계**: upsert가 잦으면 작은 파일이 폭증해 컴팩션 운영이 필수다. 테이블 포맷의
MoR/CoW 선택이 조회 성능을 좌우한다.

---

## 9. Zero-ETL / 연합 쿼리

**정의**: 복사 없이 **있는 자리에서 질의**하거나, 벤더가 제공하는 무복사 통합으로
파이프라인 자체를 없애는 방향.

**구성요소**: 연합 쿼리 엔진(Trino, Athena), 벤더 zero-ETL 통합, 외부 테이블.

**적합**: 원본 부하가 허용되고 조회 빈도가 낮을 때. 파이프라인 유지 비용이 조회 비용보다
클 때. 탐색·프로토타이핑 단계.

**한계**: 원본 시스템에 부하가 그대로 간다. 원본이 죽으면 조회도 죽는다. 대규모 조인·
반복 조회에는 부적합하다.

---

## 부록: 의미 계층 (Semantic Layer)

위 스타일들과 **직교**한다 — 어떤 스타일을 골라도 얹을 수 있다. 지표 정의를 한 곳에
두고(dbt Semantic Layer, Cube) 여러 BI 도구가 같은 정의를 소비하게 해, 도구마다
매출 수치가 다른 문제를 없앤다. 비교표의 행이 아니라 별도 절로 다룬다.

## 선택 기준표

| 조건 | 우선 검토 |
| --- | --- |
| 지연 요구가 초 단위 | Kappa, Streaming Lakehouse |
| 지연 요구가 시간·일 단위 | Modern Data Stack, Lakehouse |
| BI와 ML이 같은 데이터를 사용 | Lakehouse |
| SaaS 원본 위주, 소규모 SQL 팀 | Modern Data Stack |
| 도메인 팀이 여럿, 중앙팀이 병목 | Data Mesh (+ 셀프서브 플랫폼 투자) |
| 원본 이동이 규제·비용으로 제약 | Data Fabric, Zero-ETL |
| 검증된 배치 자산 위에 실시간만 추가 | Lambda (이중 경로 비용을 명시할 것) |
| 벤더 종속 축소가 목표 | Lakehouse (열린 포맷 + 열린 카탈로그) |

## 테이블 포맷과 카탈로그 (혼동 금지)

- **테이블 포맷** = 파일 레이아웃과 트랜잭션 규약: Apache Iceberg, Delta Lake, Apache Hudi.
- **카탈로그** = 테이블 탐색·권한·계보: Unity Catalog, Apache Polaris, Nessie, AWS Glue.

포맷을 골랐다고 카탈로그가 정해지지 않는다. 문서에서 두 결정을 각각 남긴다.
